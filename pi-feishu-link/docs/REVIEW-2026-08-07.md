## Critical（必须修复后才能宣称功能完成）

### C1. PermissionBridge 完全未接线（审批卡是死代码）

- **证据**：全库唯一调用点是 `approve()`/`deny()`（index.ts:858/864）；`evaluate()` **无任何调用**；`pi.on("tool_call")` 事件处理器**不存在**（index.ts 只注册了 session_start/session_shutdown/message_end/registerCommand/registerTool 五个钩子）。
- **影响**：spec §6.15 三级分流、README 头条「🔓 权限默认放开 / 审批卡」、欢迎卡/审批卡整套 UX 全部落空——工具调用永远不会经过权限桥。单测只测了 PermissionBridge 类本身（fake deps），测不出接线缺失。
- **修复方向**：注册 `tool_call` 事件 → 构造 paramsText → `permissionBridge.evaluate()` → ask 时挂起调用、等审批卡回调后放行/拒绝/超时。

### C2. 断连补收双 admit —— 补收功能静默失效

- **证据**：`missed-compensation.ts` `compensate()` 先 `deps.admitMessage(msg.messageId)`（写入 dedupe，返回 true）再 `onMessage(msg)` → `handleInbound` 开头 `if (!dedupe.admit(msg.messageId)) return;` —— 第二次 admit 必然返回 false → **每条补收消息都被丢弃**。
- **影响**：spec §12 #2/#4 落地项、README「断连期间消息自动补收」实际零效果。单测的 mock `admitMessage` 不会二次 admit，测不出。
- **修复方向**：补收注入走旁路（如 `handleInbound(msg, {bypassDedupe:true})`），或先判 seen（跳过旧消息）再注入且注入路径不重复 admit。

### C3. 定时任务（M6）接线断裂 —— 回投永不发生

- **证据**：index.ts:952 `bridgeRuntime?.handleMessageEnd(sessionId, undefined, message)` 传 `sessionKey=undefined`；而 `captureCreatedJobs` 第一行 `if (!sessionKey || ...) return;` → job 永不绑定。且 `beginFeishuInput()/endFeishuInput()` **全库零调用**，`activeFeishuInputs` 恒空。
- **影响**：README/CHANGELOG 声称的「说『每天 9 点总结 commit』→ 结果回投本会话」不工作。集成测试直接构造 BridgeRuntime（传了 sessionKey）所以绿，测不出 index.ts 接线。
- **修复方向**：message_end 钩子里由 sessionId 反查 conversationKey（经 ConversationManager/routes），并在桥接会话 prompt 前后调用 beginFeishuInput/endFeishuInput。

## Important（上线前应修）

### I1. 会话 FIFO 队列毒化（单次失败永久卡死该会话）

`conversation-manager.ts` `prompt()`：`next = previous.then(...)`，若 `handle.prompt`/`ensureSession` 抛错 → `next` 变为 rejected promise 存回 `queues` → **该 key 之后所有消息链到 rejected promise，立即失败**。`endTurn` 只在成功路径调用，异常路径不调用 → 恢复要等 30min 超时或 /stop 才 `disposeActiveFor` 重置队列。修复：错误路径也要 `endTurn` + 队列尾部接 `.catch(()=>{})` 兜底。

### I2. `/support` 不把诊断包发回飞书

`exportDiagnostics(msg)` 只 `replyTo(msg, 文本路径)`；状态卡 [导出诊断] 按钮 `op==="support"` 调 `exportDiagnostics()` 无 msg → 纯本地生成，飞书侧只回一句「见本地终端输出」。spec §6.17/§9.6 承诺「诊断包作为文件直接发回当前会话」未实现。修复：打包后经 outbox media 信封上传发送（可复用 `feishu_send_local_file` 的链路），并控制 ≤20MB。

### I3. 帮助卡 4 个按钮无处理器

`handleCardAction` 未处理 `resume / thinking / compact / feishu-config` 四个 op（按钮在 buildHelpCard 里渲染了）→ 点击无响应。修复：补处理器（至少回引导文本，或直接执行对应动作）。

### I4. 「停止」按钮是 no-op

`op==="stop"` 只返回文案「已发送停止请求。」，没有调用 `conversations.disposeActiveFor`。任务卡/帮助卡的 [🛑 停止] 全部假死。修复：接 TurnSupervisor/ConversationManager 的真实中止（注意 runId 防误停旧卡）。

### I5. 工具摘要 / 进度卡全链路缺失

- index.ts 会话订阅只 `extractTextDelta`，`tool_start/tool_end/progress` 事件从未进入 EventForwarder → spec §6.7 默认 `toolCalls:summary + progress:on` 从未生效，任务状态卡（buildTaskStatusCard，含 /stop 按钮）无展示。
- `TurnSupervisor` 的 `onAck/onQueueWarn` 在 index.ts 接线为 `async () => undefined`，且 `markQueued()` 从未被调用 → 「仍在处理」ack 与「排队过久提醒」全链路缺失（spec §6.4）。

### I6. 附件下载无界（内存 DoS）

`transport.downloadResource` 整流读入内存无上限；`attachment-pipeline` 的 `maxTotalBytes/maxImageBytes/maxTxtBytes` 都在**下载完成后**才检查 → 恶意 2GB 附件直接 OOM daemon。修复：下载期流式计数/提前中止，或先查 HTTP content-length。

### I7. `feishu_send_local_file` 发错会话

工具取 `Object.values(routes)[0]` —— 任意第一个已知会话，多会话场景下文件发去错误群聊，与「当前飞书会话」描述不符。修复：经当前 pi sessionId → conversationKey 反查路由（需把会话上下文传进工具执行）。

### I8. 群聊 groupPolicy 配置项无效 + README 表述失真

`classifyToolCall`：群聊时 `policy=groupPolicy`，但放行条件 `policy==="relaxed" && !group && isOwner` 中 `!group` 恒 false → **relaxed 与 strict 在群聊行为完全一致（都 ask）**。README 却声称「群聊/私聊默认宽松模式（放行+审计）」。二选一：实现群聊 relaxed 语义，或删配置项并在 README 写清「群聊一律需审批」。

### I9. 默认 `admins: []` → owner 自己被锁

`isAdminUser` 依赖配置的 admins；默认空数组 → 飞书侧 `/new /stop /model /workspace /compact /feishu-config` 全部 blocked（对包括 owner 在内的所有人），只有卡片按钮绕过。setup 流程不记录扫码者为 admin → 「零配置」承诺落空。修复：扫码流程自动写入扫码者 open_id 为 admin。

### I10. 流式卡 finalize 竞态（飞书所见 ≠ pi 所出）

outbox 定稿 patch（`outboxSender` finalize 分支）**不清 streamCards 也不停 live channel**；若 live channel 有 pending delta，flush 时会基于旧 `streamCards.text` 追加 → **把已定稿卡片覆盖成旧文本+残余 delta**。修复：finalize 前 `liveChannel.flushCard(cardId)` + 清理 streamCards 条目。

### I11. 黑名单可绕过（「永远拦截」失真）

- `/\b(sh|bash|zsh)\b[^|]*\|\s*(sh|bash|zsh)\b/` **不匹配 `curl ... | sh`**（管道前无 shell 词）。
- `rm -rf /*`、`rm -r /`（无 -f）、`rm --recursive --force /` 变体均可绕过 `rm -rf /` 模式。
修复：改为「shell 词 + 重定向/管道」组合模式 + `rm -[a-z]*r[a-z]*[a-z]* /` 通配；并给黑名单命中测试矩阵补这些变体。

## 测试覆盖缺口（为什么 170 绿却测不出这些）

1. 集成测试只验证「类 + fake deps」行为（bridge-runtime / missed-compensation / permission-bridge 单测），**不验证 index.ts 的接线**（真实调用链、sessionKey 传递、事件订阅）。
2. extension-load 测试只确认扩展可加载、banner 出现，不触发任何会话/工具/事件流。
3. 建议：加一个「真接线冒烟」集成测试（fake SDK + fake pi hooks）走通 入站 → 权限桥 → prompt → 出站 与 断连补收 两条链路，专门卡 C1/C2/C3/I1/I10。

## 优点确认

- ✅ Outbox 设计实现高质量：分航道并行、崩溃恢复重放、幂等键、压缩与容量护栏、blob 溢出——spec R1 的落地可信
- ✅ ConnectionSupervisor 静默即重建（v1.1 修正）实现正确，探针仅作诊断
- ✅ 诊断脱敏管线认真：secret 掩码、id sha256、长字符串内容默认剔除、路径归一
- ✅ 无凭据入日志（`mask(cfg.appId)`）；config/outbox 目录 0600/0700
- ✅ 纯函数拆分（group-trigger/classifyToolCall/normalizeInbound/rich-text）可测性好
- ✅ 依赖极简 + 0 漏洞
